# Edward — the door to every person, and the question after every answer

## Agent Brief

**Category:** enhancement
**Summary:** Edward becomes the entry point to every human route in the portal (Part A §12), asks
after each answer whether it worked and, when it did not, offers the routes that actually exist
(§6.4), and can be summoned at a task with that task's context already loaded (C5). This is the
mechanism the screen cards then wire into; build it once here.

**Current behavior:**

- `Edward` owns its open state internally. The only opener is its own launcher button. No prop,
  context or exported function lets another screen open it, let alone with text in the input; the
  `dialogOpen` prop only closes it. Suggestion chips call `ask()` directly and never fill the box.
- After an answer, nothing asks whether it helped. Some answers carry a person card with a
  "Message" control; the error turn keeps the question in the box with "Try again". That is the whole
  hand-off.
- Several screens offer a direct line to an office before the student has spoken to anyone:
  Appointments' no-times row and its `no-times` empty state, My Degree's credit match ("Ask the
  Registrar"), and the club card on Campus Life (the documents add "Message Dana"). Housing's "I need
  help deciding" routes to the Help page.

**Desired behavior:**

1. **The door (§12.2).** Any screen can open Edward with a question already written in the input, **not
   sent**, the panel focused on the input with the cursor at the end. The student reads it, edits it
   if the screen guessed wrong, and sends it herself. A question sent on her behalf is a conversation
   she did not choose to start; the point is to spare her the typing, not the decision. The same
   call carries the context the screen knows (the task, its office and deadline; the match; the club)
   so nothing is re-explained (C5.3).
2. **The rule (§12.1).** No route to a person appears before Edward. Two exceptions, both deliberate:
   `Book a time` from posted availability stays direct (it is a resolution, not a route), and the
   office stays named everywhere (ENR-177 AC7) — what changes is where the student starts, not who she
   can see is responsible. Each screen card does its own wiring; this card provides the door and
   states the rule on the styleguide.
3. **The question after the answer (§6.4, §8.1, §10).** After an answer, once and easy to dismiss:
   "Did that answer it?" — *Yes* / *Not really*. On *Not really*: "Let's get you to a person." and the
   routes that exist for the responsible office, never one that does not: *Book a time with
   {office}* only where that office has posted times; *Request a callback* where it has not (and the
   absence is stated); and sending an inquiry to the office, always — labelled so it never implies a
   reply to an external address (ENR-177 AC6; the §6.4 label "Email {office}" predates §8.1's
   correction and must read as an inquiry sent from the portal). Under the options: "Whatever you
   already told Edward goes with it, so you don't start over." Booking and callback are alternatives,
   not steps (§10). Declining costs nothing and leaves no item (story AC10). *Yes* leaves nothing
   outstanding.
4. **What a route produces.** Each route yields an item the student can check later, with a state that
   exposes no assignee or internal team detail; the reply arrives in the portal and email only
   notifies (ENR-177); a callback states the reply time that office publishes, never a portal
   constant (§7.2). The drawers themselves (callback request, inquiry) belong to the screens that host
   them — Appointments for the callback — but Edward offers them and passes the context.
5. **Edward at the task (C5).** A task row can carry a quiet control offering Edward with that task's
   context loaded; the question is written from the task in the student's voice, unsent. It is help
   with the task, not a route to a person. The control is a pattern (on the styleguide); My Enrollment
   hosts it.
6. **The prefilled questions (§12.4)** name the specific item, never the screen: "Academic Advising
   hasn't posted any times. How do I get in touch with them?"; "No team has posted times yet. Who
   should I talk to about my enrollment step?"; "Would my IB Spanish credit count toward Foreign
   Language, and who decides that?"; "How do I get in touch with Dana Whitfield about the Aster
   Chamber Choir?". The door takes the question as data; the screens own their strings.
7. **Edward must be able to answer** (§12.6, ENR-176): an answer about her own record, or the prompt
   in (3). Otherwise the pattern moves the dead end rather than removing it.
8. **Constraints that travel with this card.** The floating control never covers a primary action at
   any size (ENR-181's own guardrail, unchanged). No student screen hardcodes a task icon or a task
   action label (C10.3 — both are set per institution). Voice input was raised and is a wish, not a
   requirement (C5).

**Key interfaces:**

- An exported way to open Edward from a feature — a function or context the `edward` feature owns,
  taking the question text and a context object (page, task or item id, office) — plus the same
  capability on the page-level suggestion chips where they should fill rather than send.
- `Edward`'s answer turn gains the "Did that answer it?" control and the route list, fed by what the
  office has published (times posted or not; reply time) — the same data Appointments and the rail
  cards already read.
- The inline-at-task control as a design-system pattern, documented on the styleguide with the rule
  "no route to a person before Edward".

**Acceptance criteria:**

- [ ] A screen can open Edward with the input filled and unsent; the panel opens focused on the input
      with the cursor at the end; nothing is sent until the student sends.
- [ ] After an answer the student is asked once whether it resolved the question; dismissing or
      answering *Yes* leaves nothing outstanding and no item.
- [ ] *Not really* offers only routes the responsible office actually has; booking appears only where
      times are posted; where none are, the callback appears and the absence is stated.
- [ ] Every route names the office; the item it produces exposes no assignee or team detail; the
      note says the context travels with it.
- [ ] The prompt is the same regardless of which control opened Edward.
- [ ] The floating control still never covers a primary action at 1440, 820 or 390.
- [ ] The door, the prompt and the inline-at-task control are on the styleguide.
- [ ] `npm run build` passes.

**Out of scope:**

- The per-screen wiring (ENR-183, ENR-188, ENR-189, ENR-207, ENR-164 each do their own).
- The callback drawer's UI and copy (ENR-183) and the inquiry's lifecycle (ENR-177 behaviour, which
  lives in the escalation flow now that Help is not a destination — C6).
- Live chat (out of MVP). Periodic advisor meetings. Voice input.

**Domain:** the offices Edward routes to are the ones the portal already names (Academic Advising,
the Office of the Registrar, Financial Aid, Housing Services, Health Services, Accessibility
Services, Student Life); a route names the office the way the campus does — "Academic Advising", not
"the Academic Advising Office", in running text (Part A §6.1). Read `docs/domain/us-enrollment.md`
and `docs/domain/aster.md` before writing any office name or reply time.

**Blocked by:** the foundations brief (`../review-2026-08-21/brief.md`) only where the prompt's
states borrow the status vocabulary. Blocks: ENR-183, ENR-188, ENR-189 (club contact), ENR-207
(B4.2), ENR-164 (C5).
